# P0.7 evidence: GitHub organization and GitHub App

Dates: the work ran 2026-10-21 to 2026-10-22. The decommission proof ran on 2026-10-22.
Labels: Verified means checked by command or by reading the result; Observed means seen in a log or the browser; Assumed means reasoned and not tested; Open means unresolved.

## Outcome

- The platform repo and the template repo now live in the `rcarlson-platform` organization (Free plan). Argo CD kept syncing through GitHub's redirect: 14 Applications Synced and Healthy (Verified).
- The form creates tenant repos with a GitHub App installation token. The repo `form-test-1` was created that way and its image was built, scanned, signed and deployed (Verified).
- The decommission workflow deletes the tenant repo with an App token. The package delete still uses one classic token, `PKG_DELETE_PAT` (see Exception).
- `REPO_CREATOR_PAT` is deleted as a secret and the token is revoked.

## What was changed

- Organization `rcarlson-platform` created so an App installation token can create repos; the personal-account alternative needed a long-lived token for that one job (Observed from GitHub community threads, not from GitHub's official docs).
- GitHub App `rcarlson-platform-idp`: no webhook, installed on all repositories. Permissions: Contents read and write, Pull requests read and write, Metadata read, and Repository Administration read and write. No organization-level administration permission was needed. Members (read) is not granted yet; it is added in P6.3.
- Org secrets `IDP_APP_CLIENT_ID` and `IDP_APP_PRIVATE_KEY`, visible to one repo (`self-service-idp`). The private key is stored in `pass`; the original key was replaced because only its fingerprint had been saved the first time.
- `actions/create-github-app-token` pinned by full commit SHA at v3.2.0, using the `client-id` input (the `app-id` input is deprecated at that version). A newer release was rejected under the 14-day rule.
- `dispatch.yaml`: an App-token step in `validate`, `deploy_new_repo` and `populate_tenants`. `decommission.yaml`: an App-token step in `delete_github_repo`, the owner read from `GITHUB_REPOSITORY_OWNER`, the package endpoint changed to the org form. The file was also renamed from the misspelled `decomission.yaml`.
- The image signature policy now trusts `rcarlson-platform`; the template's module path and README were updated.

## Failures met on the way, and the fix for each

1. The three token steps had no `id: app-token`, so the token expression was an empty string. `validate` still passed, because it treats any failed call as "does not exist"; `deploy_new_repo` failed. Fix: add the id. Lesson: count definitions, not only uses.
2. HTTP 422 `Invalid owner`: the template generate endpoint defaults the owner to the authenticated identity, which is the bot for an App token. Fix: pass the owner explicitly.
3. HTTP 403 `Resource not accessible by integration`: the App lacked Repository Administration. Fix: grant it and approve it on the installation.
4. The first tenant build was blocked by Trivy: a HIGH finding in the Go standard library (`crypto/x509`), as reported by Trivy, not independently checked. Fix: bump Go from 1.27.2 to 1.27.3 in five places. No ignore entry and no threshold change.
5. Kyverno refused the deployment: the image package was private, so an anonymous token request returned `UNAUTHORIZED` and the policy, which fails closed, could not verify the signature. Fix: make the package public after the org setting that allows public packages was enabled. After that, all resources deployed.

## Decommission proof (2026-10-22)

`make smoke` exit 0 before. The workflow ran with all four jobs `success`. Because the package check hides errors, each result was read back separately:

- The repo API call returned 404 (Verified).
- The anonymous tag-list request returned `NAME_UNKNOWN`, so the package is gone (Verified). This shows the personal token works against the org package endpoint.
- `argocd/tenants` held only `sentinel-configmap.yaml`; no `form-test-1` directory.
- Namespace `form-test-1` remains; the `-db` namespace is gone (the known empty-namespace defect, R22).
- 14 Applications Synced and Healthy; `make smoke` exit 0.

## Exception: one personal token

GitHub's REST documentation for packages says managing packages needs a classic personal access token; App installation tokens are listed only on the read endpoints (Observed from the documentation; the App token was not tested against the delete endpoint). `PKG_DELETE_PAT` has scopes `delete:packages` and `read:packages`, was regenerated on 2026-10-22 with an expiry of 2027-01-20, and has a calendar reminder two weeks before. It moves to a protected environment in P6.5. Risk register row R08.

## Proof against the plan's "Prove it"

Search of `.github/` in the platform repo for secret references to a token or PAT found only `GITHUB_TOKEN` (the automatic per-run token, three lines) and `PKG_DELETE_PAT` (one line). Verified. `create-github-app-token` appears once in `decommission.yaml` and three times in `dispatch.yaml`. The template repo was not searched, because its workflow runs only in tenant repos (Actions is disabled on the template by design) and it uses only the automatic token to push to the registry (Assumed).

## Differences from the plan

- The plan said organization administration read and write might be needed; repository Administration was what the template generate call needed.
- Store the client ID, not the App ID.
- The package delete endpoint is the organization form, not the user form.
- The plan said the decommission workflow would use an App token throughout; the package delete cannot.

## Not done, or not known

- The App token was not tested against the package delete endpoint (Open; the documentation says a classic token is needed).
- The image policy probably checks only images that match its glob, so an unsigned image from another registry might run (Assumed, not tested; R21).
- The signer identity ends in a wildcard, so every repo in the org is trusted (R20).
- Both workflows' pushes to `main` appear to use the automatic token; a ruleset bypass for the App will not cover them unless those jobs use the App token (Assumed; check at the start of P0.3).
- `actions/checkout@v7` is unpinned in two places (`dispatch.yaml` and `decommission.yaml`); P1 pins it.
- Several checks treat any error as "does not exist", so a job can pass with a broken token (R23).
- The capacity ledger row for the extra tenant moves to P0.5, since the tenant is gone.
